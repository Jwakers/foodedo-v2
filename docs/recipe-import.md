# AI recipe import

Normalization version 9 applies to new URL/text imports and retries only. Existing recipes, catalogue content and plan snapshots are unchanged.

## Pipeline

1. `source.ts` collects whole readable-page and JSON-LD blocks under the source budget. Every block has a stable ID. Relevant Recipe fields are flattened with property paths and bounded graph references resolved, without parsing ingredient names or choosing a cooking method. Recipe cards have priority, article/main content supplies missing context, and structured evidence follows. Empty jump anchors cannot hide the article. Tables retain row/cell boundaries; nested lists retain separate items. Pasted lines carry position-based identities so identical ingredients in distinct components remain separate evidence. Truncation is explicit.
2. `extraction.ts` always calls the configured model using the schemas and prompts in `models.ts`. The response is tagged as recipe, no recipe or incomplete recipe. Non-recipe responses have no dummy recipe fields. An incomplete assessment is independently audited and enters the same single repair allowance; only confirmed missing ingredients/method after repair produce an incomplete failure, with bounded missing-area diagnostics. Unconfirmed assessments exhaust as normalization failures, not claims about absent source content.

3. `validation.ts` checks IDs, measurements, balanced ingredient fields, notes and durable content bounds. Measurement evidence is supported, conflicting or inconclusive. Unfamiliar notation, qualitative amounts and unspecified amounts need explicit positive confirmation from the separate AI verifier, not merely an empty findings list. The verifier audits formatted consumer-facing amounts and resolved notes for coverage, quantity scope, preparation, alternatives and cooking sequence. Concrete findings drive one complete repair and another audit. All findings participate in save eligibility; only persisted diagnostics are bounded. Repair detail is transient and never persisted. There are no specialist models or deterministic recipe fallbacks.
4. `measurements.ts` formats typed amounts into existing recipe fields. `pipeline.ts` keeps owner-scoped job orchestration, atomic saving, fingerprints and asynchronous image attachment.

Pasted ingredients and a usable method suffice without a heading or metadata. AI synthesizes a factual title/description from those blocks (title references cite the supporting ingredients/method), never inventing quantities or instructions. Unknown optional metadata remains absent and saves through the existing needs-review contract. Success copy discloses suggested metadata and links directly to the existing full editor for title, description, servings and timing amendments. This does not introduce storage of unverified partial cooking instructions or a second editing workflow.

At most two extraction and two verification calls are allowed. A processing attempt has a shared deadline 110 seconds after it is claimed, leaving time before the existing 120-second watchdog. Provider SDK retries are disabled; each call is cancelled at the remaining deadline. A valid source can still fail because fetching or AI is unavailable. No unsuccessful AI result is saved.

Malformed or missing SDK structured output enters the bounded repair path; outages and deadline exhaustion retain separate failure codes. Every fetched body is consumed/cancelled and its dispatcher destroyed on completion or rejection; cleanup errors cannot replace the original failure. Signed-out job links request sign-in before rendering progress and retain the existing job URL. Pending draft continuation cannot replace an existing job link, and retry submissions are guarded while pending.

## Measurements

Verification findings internally identify disputed numeric metadata fields. After the single repair, if every remaining finding concerns only a specifically identified non-published optional servings/time value, that value is omitted and deterministic validation runs again. Verified ingredients/method stay intact; published metadata, lost qualifiers/notes, uncertain measurements and unclassified findings never use this recovery. No replacement estimate or extra model call is introduced.

The existing primary model stays `openai/gpt-5.4-mini`. Prompts and configuration live together in `models.ts`: extraction, verification and repair use explicit low reasoning. This avoids the model's non-reasoning default while leaving deadline capacity for repair; medium reasoning was too variable on the complex live recipes. The injected client remains replaceable. Supported effort levels are documented by [OpenAI](https://developers.openai.com/api/docs/models/gpt-5.4-mini).

The internal amount union has exact, range, package, qualitative and unspecified variants. Display text is generated by code, never independently authored by AI.

- Published g/kg/ml/l equivalents take priority. Otherwise lb/oz weights convert with exact international factors and round to three significant figures. Cups, tsp/tbsp and meaningful count units stay as published; density conversions are not permitted.
- Fractions are numeric decimals internally. Exact quantities use up to six decimal places with trailing zeros removed; ranges use an en dash. Ordinary item counts have no display unit.
- Packages retain count and size: `2 × 400 g cans`. They are not replaced by aggregate weight. Each shared EACH ingredient receives the original amount and source evidence reference.
- Equivalent units joined by “or” still describe one amount, not a second ingredient choice. Differently quantified ingredient choices keep the first identity/amount and the full alternative in a note. Counted items with per-item weight ranges keep an exact count and retain the weight information in their note, not a fabricated count range or package.
- Qualifiers such as heaped are retained. To taste, handfuls and unknown quantities are not estimated. Size/variety qualifiers belong in names; preparation belongs in notes.
- Hyphenated measurements such as `250-gram` are valid evidence. An article-led package has count one only when a container noun and numeric size are actually present. Descriptive sizes such as a small can are retained without inventing a weight. Differently quantified alternatives use one line with the first choice's amount/name and the other choice's quantity/name in its note; they are never ranges or simultaneous purchases. Identical rows in different recipe components retain separate amounts.
- Measurement validation compares dimensions and equivalent values with a 0.6% tolerance for authored/converted rounding, rather than matching literal numeric tokens. Unicode fractions and fraction slashes are normalized for comparison only. Checklist markers and size-qualified counts such as `▢ 3 large cloves` remain valid evidence. Unrecognized notation is independently confirmed, not automatically rejected. Semantic validation separately checks recipe content, including legitimate numeric names such as 5-spice powder.
- Scaling stays all-or-nothing under the existing contract: unsupported amounts, qualifiers, packages, ranges and qualitative/unknown amounts use `source_only`.

## Timing

`timing.ts` defines one shared extraction/verification policy. The AI must distinguish total time from prep/cook, derive sequential cooking phases without double-counting concurrent work, and estimate ordinary untimed preparation from the actual tasks. Published components take precedence; inferred splits reconcile with a trustworthy published total. Ranges use their upper bound for integer metadata while retaining the authored range in the method. A missing label alone is not grounds for missing timing.

Explicitly timed preparation actions have derived provenance, just like timed cooking actions. Estimates apply only when untimed work contributes to the number. Yield ranges and prep-time qualifiers also remain in recipe notes because the numeric metadata fields cannot preserve them.

The internal `timingBasis` carries a bounded factual summary, total-time evidence and an explanation for genuinely unresolved timing. It is independently audited and checked for source IDs and arithmetic, then discarded before persistence. Only the existing times and published/derived/estimated provenance are saved. No timing parser, extra model calls or public schema changes are introduced. Open-ended waits and genuinely conflicting evidence can remain unknown; estimated metadata never invents recipe instructions or ingredient quantities.

## Diagnostics and compatibility

Jobs store only bounded failure areas, whitelisted reason codes and evidence IDs; retry and success clear them. Logs do not contain credentials, source content or model responses. Normalized lines preserve bounded original expressions for the owner's edit recovery. The legacy ingredient recovery helper remains only for the existing editor's **Use original** action, never as an importer path.

## Verification

Unit tests use injected clients for normalization, repair, semantic rejection, timing arithmetic, actual SDK contract errors, outages and non-recipe responses; Convex tests verify atomic job persistence and sanitized diagnostics. Mocked network tests cover body/dispatcher cleanup without disabling production SSRF checks. The corpus includes source-layout, measurement, method and overlapping-timing fixtures plus the three reported live URLs. Independent ingredient, method-action, temperature/duration and note assertions replace unconditional semantic-success metrics. Timing cases assert component values, total reconciliation and provenance, not just import success. `pnpm eval:recipe-import` requires an AI Gateway key, calls actual providers, checks explicit output expectations and exits non-zero on a failed acceptance case; `--case=id,... --repeat=3` checks repeated cases (maximum five runs). Never commit keys or run automatic evaluations in ordinary unit tests.

Before development sync, pass unit/Convex checks, formatting, lint, typecheck, both builds and the live corpus. After sync, use the authenticated import UI to create a fresh reported recipe and inspect the persisted amounts, ingredient names, instructions and timing provenance.
